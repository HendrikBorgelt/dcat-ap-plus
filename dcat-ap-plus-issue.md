# Proposal: Structured content description and provenance layer for DCAT-AP — the `DataGeneratingActivity` pattern

## TL;DR

DCAT-AP provides robust dataset cataloging but lacks structured ways to express *what* a dataset is about or *how* it was generated. While `prov:wasGeneratedBy` is present, the linked `Activity` has no specified properties in DCAT-AP 3.0 — it is a structural dead end. We have developed **DCAT-AP+**, a domain-agnostic provenance extension that fills this gap using PROV-O's Starting Point Terms, and we present it here as a reference implementation and formal proposal for discussion and potential upstream consideration.

We are open to changes in the concrete modeling choices and welcome your feedback. We do, however, believe that the core need — structured, machine-actionable provenance and content description for datasets — is real and shared across research domains, and we would like to see it addressed in a future revision of DCAT-AP.

---

## 1. The gap in DCAT-AP

DCAT-AP provides three mechanisms to describe a dataset's subject matter:

| Property | Limitation |
|---|---|
| `dcterms:description` | Free text — not machine-actionable |
| `dcat:keyword` | Free text — not machine-actionable |
| `dcat:theme` | Controlled by the [EU Dataset Theme Vocabulary](https://op.europa.eu/s/zXIN) — too coarse for domain-specific discovery (e.g., no way to distinguish NMR from IR spectroscopy) |

For describing how a dataset was created, DCAT-AP provides `prov:wasGeneratedBy` linking to a `prov:Activity`. However, this `Activity` node shape has **no specified properties** in DCAT-AP 3.0 — it is classified as a "Supportive Entity" and effectively a structural dead end. You can say a dataset was generated by *some activity*, but not *what kind of activity*, *what was evaluated or measured*, nor *which instruments were used*. This prevents machine-actionable discovery across data portals.

---

## 2. Further problems this proposal addresses

### Fragmented content description across research domains

Existing DCAT-AP profiles demonstrate that the need for richer content description is widely recognized — but each domain has addressed it independently, producing a fragmented landscape:

- **[GeoDCAT-AP](https://semiceu.github.io/GeoDCAT-AP/releases/3.0.0/)** adds `geodcatap:topicCategory` (ISO 19115 topic categories: agriculture, environment, elevation, ...) and refines agent roles (`geodcatap:originator`, `geodcatap:principalInvestigator`). It describes what a dataset is about through controlled-vocabulary classification applied to the dataset itself. `prov:wasGeneratedBy` is technically present, but its documented use is limited to conformance testing results — not the original data collection activity.

- **[HealthDCAT-AP](https://healthdataeu.pages.code.europa.eu/healthdcat-ap/releases/release-5/)** adds `healthdcatap:healthCategory` (EHDS Article 51 categories: EHR data, genomic data, clinical trial data, ...), `healthdcatap:codingSystem` (ICD-10, SNOMED-CT, LOINC), and `healthdcatap:populationCoverage`. Content is described through layered classification and scope metadata applied directly to the dataset. The data-generating activity (the clinical measurement method or study design) is not modeled.

- **[StatDCAT-AP](https://interoperable-europe.ec.europa.eu/collection/semic-support-centre/solution/statdcat-application-profile-data-portals-europe/release/101)** adds `stat:dimension` (SKOS codelists for how observations are disaggregated: by time, geography, age, sex) and `stat:attribute` (units, scaling factors, observation status). This describes the structure of what is measured, but not the substantive phenomenon itself — the topic still relies on inherited `dcat:theme` and `dcterms:subject`.

Each profile solves its domain's content description need effectively within that domain. However, the approaches are not mutually compatible: a `geodcatap:topicCategory`, a `healthdcatap:codingSystem`, and a `stat:dimension` all serve the same semantic purpose — relating a dataset to its subject matter — but share no common structure. Cross-domain queries like *"find all datasets that evaluated substance X, regardless of whether they appear in an environmental, health, or chemical data portal"* remain impossible.

Notably, none of these profiles model the **data-generating activity** as a vehicle for content description. DCAT-AP+ takes a fundamentally different approach: rather than adding more classification layers to the dataset, it describes *what was done* and *what was evaluated* during data collection — a shared activity-level structure that works across all research domains without requiring per-domain classification properties to be aligned post-hoc.

### Problems in DCAT-AP extension practice

The [SEMIC blog post on Application Profile modelling](https://interoperable-europe.ec.europa.eu/collection/semic-support-centre/application-profiles-what-are-they-and-how-model-and-reuse-them-properly-look-through-dcat-ap) identifies six problems with current DCAT-AP extension practices. DCAT-AP+ directly addresses three of them:

**Problem #2 — Inconsistent artefact generation.** Published specification artefacts (HTML docs, SHACL shapes, JSON Schema) are often generated by different tools or edited manually, leading to inconsistencies between them. DCAT-AP+ uses **LinkML as a single source of truth**: one YAML schema generates SHACL shapes, JSON Schema, Python/Pydantic data classes, and HTML schema documentation coherently.

**Problem #5 — Disadvantages of generalisation.** The recommended approach for semantic adaptation in DCAT-AP extensions is to create subclasses. This hinders adoption: if every domain creates its own `dcat:Dataset` subclass, interoperability requires reasoners or explicit multi-typing. DCAT-AP+ avoids subclass proliferation through its `ClassifierMixin`, which uses `rdf:type` to classify instances with domain-specific ontology terms *without* introducing new OWL subclasses — an approach explicitly endorsed by SEMIC.

**Problem #6 — No entity profile mechanism.** There is no established way to define multiple usage profiles for the same entity. DCAT-AP+ addresses this through its LinkML-based approach: multiple classes can reference the same ontology term (e.g., `prov:Entity`), each acting as a distinct SHACL node shape with its own constraints and shape IRI.

## 3. The proposed extension: `DataGeneratingActivity`

We propose filling the empty `Activity` shell by specifying a `DataGeneratingActivity` shape, aligned to `prov:Activity`, that adds the structured provenance context currently missing from DCAT-AP.

`DataGeneratingActivity` extends the base Activity pattern (inputs, outputs, responsible agents — the PROV-O Starting Point Terms) with four slots specific to data production:

| Slot | Mapped to | Purpose |
|---|---|---|
| `evaluated_entity` | `prov:used` (narrowed range) | The entity being measured, observed, or analysed |
| `evaluated_activity` | `prov:wasInformedBy` (narrowed range) | A prior process being studied |
| `realized_plan` | `prov:used` | The protocol or method followed |
| `occurred_in` | `prov:atLocation` | The spatial context (lab, field site, ...) |

The inherited base slots cover instruments (`carried_out_by` → Device / Software, aligned to `prov:wasAssociatedWith`), input/output entities, and quantitative/qualitative attributes (see [Section 5](#5-structured-attribute-description)).

**Example:** The following is a valid DCAT-AP+ instance record describing a ¹³C NMR measurement. All predicates map to existing PROV-O and DC Terms properties; the instance can be validated and converted to RDF using standard LinkML tooling:

```yaml
id: ex:dataset-001
title: "13C NMR spectrum of aspirin"
was_generated_by:
  - id: ex:measurement-001
    rdf_type:
      id: CHMO:0000595           # "carbon-13 NMR spectroscopy" (Chemical Methods Ontology)
    evaluated_entity:
      - id: ex:sample-001
        rdf_type:
          id: OBI:0000747         # "material sample" (Ontology for Biomedical Investigations)
        has_quantitative_attribute:
          - value: 298.0
            has_quantity_type:
              id: qudt:Temperature
            unit:
              id: qudt:K
    carried_out_by:
      - id: ex:spectrometer-001
        rdf_type:
          id: OBI:0000625         # "JEOL ECX NMR spectrometer" (OBI)
```

This enables SPARQL queries like *"find all NMR datasets measured at temperatures between 290 and 310 K"* — impossible with plain DCAT-AP's free-text description.

## 4. Subject matter: `EvaluatedEntity` and `EvaluatedActivity`

A key aspect of DCAT-AP+ is the explicit distinction between *what was used as input* to an activity and *what was the subject of study*. A sample, for instance, may be consumed as input during a measurement — but it is also the *thing being evaluated*.

DCAT-AP+ addresses this with two sub-slots of narrower semantic range:

- **`EvaluatedEntity`**: a `prov:Entity` that is the specific subject of the measurement — the sample, specimen, or artifact being studied. It is a sub-slot of `had_input_entity` (mapped to `prov:used`) with a narrower range, following the DCAT-AP extension guideline that "properties may be added, but must not duplicate existing ones."
- **`EvaluatedActivity`**: a `prov:Activity` that is itself the subject of study — e.g., a prior process being re-analysed. Analogously a sub-slot of `had_input_activity` (mapped to `prov:wasInformedBy`).

DCAT-AP+ links subject matter to *both* the `Dataset` and the `DataGeneratingActivity` — intentional redundancy that supports two complementary query patterns:

- **Dataset-centric**: *"Find all datasets about substance X"* → query `is_about_entity` on the Dataset
- **Process-centric**: *"Find all activities that evaluated substance X"* → query `evaluated_entity` on the Activity

Both slots are mapped to `dcterms:subject`, with `exact_mappings` to `IAO:0000136` ("is about" from the Information Artifact Ontology). This dual linking allows FAIR data portals to answer both cataloging and process-oriented discovery queries without requiring reasoners.

It is worth noting that this pattern can also address the **categorization need** that domain-specific profiles currently solve with flat classification properties (such as `geodcatap:topicCategory` or `healthdcatap:healthCategory`). Because `EvaluatedEntity` and `DataGeneratingActivity` both carry `rdf_type` slots (via `ClassifierMixin`), typing the evaluated entity or the activity with a domain ontology term — e.g. an EHDS health category concept, an ENVO environmental feature class, or a CHMO measurement type — produces the same categorical signal, but grounded in *what was actually studied or done* rather than attached as a flat tag to the dataset. The categorization emerges from the structured description of the generating activity, rather than requiring a separate domain-specific classification property. Domain profiles can of course still add dedicated category properties on top of this foundation where needed.

## 5. Structured attribute description

Beyond subject matter, domain-specific metadata typically involves quantitative or qualitative properties — temperatures, concentrations, instrument settings, calibration standards. In plain DCAT-AP, these can only be encoded as free text in `dcterms:description`. DCAT-AP+ provides two structured classes:

- **`QuantitativeAttribute`** (aligned to `qudt:Quantity`): a single-node pattern carrying `value`, `quantity_kind`, and `unit` — enabling precise range queries. From the example above: the measurement temperature of 298.0 K is directly queryable and comparable across datasets.
- **`QualitativeAttribute`** (aligned to `prov:Entity`): a string `value` with ontology-grounded classification via `rdf:type` — enabling semantic filtering. Example: filtering by NMR pulse program type using the NMR ontology, or by assigned InChIKey structure.

Both can be attached to entities (the sample), activities (the measurement process itself), or agents (the instrument) via `dcterms:relation`. The pattern is deliberately minimal — a single hop from subject to value — aligned to [QUDT](https://www.qudt.org/)'s `Quantity` model, making it accessible to data producers who are not ontology engineers. Domain profiles that need richer attribute structures can subclass either pattern and add the necessary additional nodes.

For detailed examples and the design rationale, see the [Design Patterns documentation](https://nfdi-de.github.io/dcat-ap-plus/latest/design-patterns/).

## 6. Why PROV-O?

DCAT-AP already references PROV-O — `prov:wasGeneratedBy` is part of the existing specification. Our proposal extends this existing commitment rather than introducing a second provenance vocabulary.

We evaluated alternatives before settling on PROV-O's Starting Point Terms:

- **[SOSA/SSN](https://www.w3.org/TR/vocab-ssn/)**: Well-suited for sensor networks and hard-science measurements, but assumes the *sensor → observation → observed property* model. A humanities corpus annotation or a social-science survey does not fit: there is no "sensor" and no "observed property" in the SOSA sense. Data producers from these fields should not be forced into an observation-centric vocabulary.
- **[P-Plan](http://vocab.linkeddata.es/p-plan/index.html)**: Designed for experimental workflows with explicit `Plan → Step → Variable` structures. More expressive than needed and assumes a structured, step-by-step execution model that does not generalise to all research contexts.
- **[ProvONE](https://purl.dataone.org/provone-v1-dev)**: A PROV-O extension for computational pipelines (`Program`, `Port`, `Channel`). Fits computational workflows well but does not generalise to empirical, observational, or humanities data generation.

PROV-O's Starting Point Terms — `Activity`, `Entity`, `Agent`, `used`, `wasGeneratedBy`, `wasAssociatedWith` — are intentionally abstract and cover all these cases without imposing domain-specific assumptions. Domain profiles add precision on top: [ChemDCAT-AP](https://github.com/nfdi-de/chem-dcat-ap) adds chemical substance classes; a sensor-network profile could map `DataGeneratingActivity` → `sosa:Observation` via `exact_mappings` without changing the base layer.

A formal [mapping between PROV-O and the Basic Formal Ontology (BFO)](https://doi.org/10.1038/s41597-025-04580-1) has been published, validating alignment with OBO Foundry ontologies used by research communities across the natural sciences.

## 7. Modeling approach: SHACL shapes, not new OWL classes

DCAT-AP+ is an **application profile** — a graph shape specification, not an ontology. We use [LinkML](https://linkml.io/) as a single source of truth: one YAML schema generates SHACL shapes, JSON Schema, Python/Pydantic data classes, and HTML schema documentation, ensuring all artefacts remain coherent.

DCAT-AP+ classes are **SHACL node shapes** that reference ontology terms via `class_uri` — they do not introduce new OWL subclasses. Multiple shapes can reference the same ontology term, each representing a different usage profile of that term with its own constraints and shape IRI. This avoids the subclass proliferation that hinders interoperability in current DCAT-AP extension practice. (See [Section 2](#2-further-problems-this-proposal-addresses) for the SEMIC problem context.)

The full extension as a UML class diagram (red = DCAT-AP+ additions; green classes carry `rdf:type` / `dcterms:type` classification slots via ClassifierMixin):

![DCAT-AP+ UML class diagram](https://raw.githubusercontent.com/nfdi-de/dcat-ap-plus/main/docs/images/DCAT-AP-PLUS_UML_only_light.svg)

Reading guide: **Dataset** (top left) links to a **DataGeneratingActivity** via `prov:wasGeneratedBy` and to subject matter via `dcterms:subject`. **DataGeneratingActivity** (centre) links to its evaluated entity/activity, agents (Device/Software), an optional Plan, and an optional Surrounding. **QuantitativeAttribute** and **QualitativeAttribute** (right) attach to entities, activities, and agents via `dcterms:relation`.

## 8. How domain profiles extend this

DCAT-AP+ is designed as a building block. Any domain profile can import it and specialize it by:

- Subclassing classes (e.g., `SubstanceSample is_a EvaluatedEntity` in ChemDCAT-AP, mapped to `SIO:001378`)
- Creating sub-slots with narrower ranges or domain-specific RDF predicates
- Adding domain-specific classes and enumerations

[ChemDCAT-AP](https://github.com/nfdi-de/chem-dcat-ap) (chemistry and catalysis) is the first published domain profile. Detailed extension rules are documented in our [Rules for domain profiles](https://nfdi-de.github.io/dcat-ap-plus/latest/how-to-extend/).

## 9. Request and call to action

We are aware that incorporating a provenance layer into DCAT-AP is a significant change, and we are genuinely open to feedback on the concrete modeling choices presented here. The core need — a structured, machine-actionable way to describe *what* a dataset is about and *how* it was generated — is, we believe, real and widely shared across research communities and data portals.

We would welcome:

- **Feedback** on whether and how this pattern could inform a future revision of DCAT-AP
- **Discussion** of the modeling choices (PROV-O alignment, sub-slot pattern for EvaluatedEntity/Activity, dual linking, SHACL shape approach)
- **Pointers** to parallel work or existing proposals we may have missed
